## 2. GPU 占用升高的优先候选

### G1：呈现吞吐变化，没有独立的 VRR 输出预算

定位：`PresenterBase.cpp:158–180`、`AdaptivePresenter.cpp:167–228`、`Renderer.cpp:938–970, 1441–1531, 3108–3180`、`include/FramePacingOptions.h:69–75`。

开／关都调用 `Present(0, flags)`，区别是开启且合格时带 `DXGI_PRESENT_ALLOW_TEARING`。普通输出和 XeSS 仍保留 frame-latency／SDK 等待；这种容量约束不等于固定 FPS 限制。共享 `_UpdateFrameRateLimits()` 合并现有最大帧率、过滤效果和帧同步目标，**没有根据 VRR 开关增加输出预算**。帧同步自动目标使用 `refreshRate / multiplier`，目前也没有专门的 VRR 上限余量。

推断：如果先前受到呈现队列／驱动节流，VRR 生效后可提交更多内容帧、生成帧或辅助帧，每秒 GPU 工作会增加。是否确实如此必须读取提交计数和 GPU 时间；源码并不能证明开启 tearing 必然解锁 FPS。DLSS 的基础帧率与生成帧输出率、XeSS 的输入率与 SDK 最终输出率分别统计。

解决方向：先做等输入／等输出帧率对照。若确认多余提交，复用现有限帧所有者修正缺口；VRR 上限策略作为明确的预算设计，不再添加一个与 StepTimer／Front Edge／Reflex／XeLL 竞争的独立 sleep。只在需要时设计刷新率余量；数值由实际输出间隔决定。

### G2：前台兼容可能同时影响驱动后台限帧／性能策略

定位：`NvidiaForegroundCompatibility.cpp:159–187, 226–246`。

当前 Hook 是 Magpie 进程内 `GetForegroundWindow` 的 API 级 Hook。命中 NVIDIA UMD、DXGI、D3D11 的模块范围且会话合格、真实源前台时，返回输出 HWND。**筛选依据是模块范围，并没有区分该查询用于 G-SYNC、后台 FPS 限制还是其他驱动判断。** 实际源游戏输入焦点保持原状。

NVIDIA 提供后台应用最大帧率和电源管理设置。因而，“开启兼容使 Magpie 脱离后台节流，增加实际提交／改变功耗状态”是有依据的待验证假设；公开资料没有证明当前驱动用本 API 实现这些策略。不得据此宣称已确认驱动内部机制。

解决方向：记录 `Magpie.exe` 与源应用的驱动程序配置；比较标准层、Trace 和完整模式的提交率／GPU 时间／频率／功耗。若命中该假设，先由应用输出预算承接；仅在采集到明确调用点后再评估缩小覆盖范围。SDK 后台查询仍需支持，不能只允许前端线程或同步 Present 的 TLS 区间。

### G3：更多辅助重绘会放大全画面复制／合成

定位：`Renderer.cpp:1046–1077, 1123–1141, 1218–1289, 1315–1342`、`FramePresentationTiming.h:64–88`。

普通／DLSS 输出每次前端绘制会复制场景、绘制叠加层／光标；成功内容提交后还更新稳定画面副本。辅助提交可重绘上一幅完整画面。辅助节流按显示器标称刷新率运行，关键输入／部分光标状态可立即提交。现有无脏数据检查、辅助限速和 DLSS FIFO 优先策略已经存在，**尚未发现 VRR 会强制绕过这些保护**。

推断：呈现机会增加后，光标、性能面板、参数界面或最低重绘要求可能消耗更多 GPU Copy／3D 工作，尤其高分辨率或低内容 FPS 场景。是否存在过量辅助提交尚待计数。

解决方向：分开统计内容、生成帧、光标／叠加层、强制／空闲重绘的提交原因与 Copy／Draw 数量。若辅助工作确实主导增量，再修正脏数据合并和辅助预算，保持首击／按键边沿／可见性变化及时响应。

### G4：同帧率下检查驱动、DWM 和占用读数的变化

若 G1／G3 提交率基本相同，比较 Magpie、源程序及 DWM 的 GPU 引擎忙时、频率、功耗和每帧 GPU 时间。占用百分比、功耗和每帧成本分别记录。仅频率／功耗或呈现模式变化时，不将其归为新增效果计算；若等帧率下 GPU 每帧时间变长，再定位具体 Copy、Draw、合成或 SDK 队列。

`FrameTrace.h` 明确只记录 CPU wall time；当前 DLSS 前端 draw／endFrame 统计也是 CPU 耗时。效果 GPU profiler 只覆盖其效果范围，不覆盖所有前端复制／DWM／SDK 最终呈现。不得用这些 CPU 数字替代 GPU 执行时间。

## 3. 源码中确认存在的 CPU 性能隐患

| 项目 | 已确认的工作 | 影响与优化方向 |
| --- | --- | --- |
| C1 前台查询热路径 | `DetourForegroundWindow()` 每次读取完整发布快照；符合覆盖条件时执行源／输出窗口身份、根关系、可见性等检查，并二次确认真实前台。正常源、输出各自与 root 相同时仍重复 `Matches` | 优先去重相同窗口身份检查，给非目标调用快速返回；保留句柄复用、隐藏／最小化、退休和真实前台变化保护。CPU 成本待测 |
| C2 默认诊断原子操作 | 每个目标查询增加 `targetQueries`；每次成功覆盖增加 `appliedQueries`；每次调用 `Record()`，已观察的目标 phase 仍执行共享 `fetch_or`。未知调用仍扫描最多 16 个观察槽 | 普通模式精简统计；已观察标记先 load 再决定 RMW，详细观测由显式诊断入口控制。跨线程共享计数可能产生竞争，尚无实测 |
| C3 发布状态过大／反复发布 | 快照含 6 个身份和 8 个模块范围。Windows x64 布局推导为 288 字节，即 36 个原子 word；读取整个快照后才筛选调用者。发布采用默认顺序一致的逐 word store，即使内容未变仍更新版本 | 拆分热判定与诊断身份；无变化不发布。设计经过验证的发布／读取协议，不能仅把所有操作改为 relaxed，也不能引入无界自旋或不安全裸结构 seqlock |
| C4 周期扫描在前端线程 | `Poll()` 每秒 `CreateToolhelp32Snapshot`／遍历 Magpie 进程的全部模块／重复 PIN 已知 DLL／重新 Publish；`_RefreshVRREnvironment()` 每 500ms 查询适配器与输出枚举 | 可能引入周期性 CPU／帧时间尖峰。模块范围缓存、尚未加载模块的低频发现；显示拓扑／移动／Resize 触发重新资格检查，并保留低频恢复探测 |
| C5 常规日志与每帧身份采样 | Poll 中查询计数变化使 `LogState("sample")` 稳定每秒触发；`FrontendWindows()` 从 `_UpdateSrcState()` 路径重新读取参数身份／前台。日志使用同步 `rotating_logger_mt` | 常规模式仅状态变化／错误日志，详细统计聚合；复用已经读取的真实前台并在宿主变化时登记身份。Info 并非每帧 flush，当前 Release 周期 flush 为 30 秒，不能描述为每次查询写盘 |
| C6 无效兼容模式仍经过 Hook | Prepare 在知道 GPU vendor 前安装 Hook；非 NVIDIA Query 后转 Off，或后续 Reject 转 Off，Hook 直到 FinishRetire 才禁用；Detour 仍先读取快照再判 Off | 增加轻量 Off／不合格快速路径，评估在可靠生命周期边界关闭 Hook。保留原始 trampoline 和在途调用保护，不能直接释放 |

正常 source/root、output/outputRoot 均有效、已显示且相同句柄时，覆盖分支的源／输出验证合计有 **19 次窗口状态／身份 API 调用**，另有首尾真实前台读取和 LastError 保护；记录首次观测时还会分类。这是源码调用数量，不是耗时测量。

历史 Beta2 日志复核：epoch=5（旧 FG 排除、`armed=false`）138 个约一秒样本区间的目标查询中位数约 **1200 次／秒**；无 FG 的多个 armed 会话中位数约 **300–391 次／秒**。这些计数说明 `GetForegroundWindow` 热路径不是偶发操作；epoch=5 未执行覆盖窗口检查，且当前版本具体频率可能不同。必须重新采集本次反馈场景。
